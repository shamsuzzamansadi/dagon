## 1. What is being built

*DAGON: Beneath the Black Tide* is a 10–15 minute 2D side-scrolling cinematic
horror game for a game jam (7 focused days), based on Lovecraft's public-domain
story *Dagon*.

- **Platforms:** Windows and Linux. Web is a stretch goal.
- **Tech:** Godot 4 + C++20 via GDExtension (godot-cpp), built with SCons.
- **Player verbs:** walk, small jump, interact. An always-on lantern.
- **No** combat, death, inventory or saves.
- **Level:** one continuous level in four acts: Shore → Exposed Abyss →
  Monolith (puzzle) → Witness (scripted reveal of a colossal creature, a short
  flee, collapse, epilogue).
- **Puzzle:** press three glyph stones in story order (Wave → Kneel → Eye).
  - Clues come from three tablets earlier in the level and from the mural.
  - A wrong press dims all stones, locks input for 1 s, then resets.
  - Only 6 orderings exist, so trial and error always works. Solved is
    terminal.
  - There are no one-way drops, so the player can never be softlocked.

## 3. Proposed architecture

**Principles:**
- Use Godot's systems (CharacterBody2D, Area2D, AnimationPlayer, Parallax2D,
  2D lights, Tweens).
- No autoloads or singletons. All state lives in the level scene, so restart is
  `reload_current_scene()`.
- Editor-wired signals. No event bus.
- No GDScript in shipped code (tests only).
- Deterministic rules in plain C++ with no Godot headers, so they can be
  unit-tested natively with doctest.

**GDExtension classes (namespace `dagon`):**

| Class | Base | Responsibility |
|---|---|---|
| PlayerController | CharacterBody2D | Walk, gravity, jump (coyote, buffer, variable height), facing, animation, footstep signal. `set_control_enabled`, `teleport`. Movement maths delegated to `core::step()`. |
| Interactable | Area2D | `interaction_id`, prompt, caption, `one_shot`, `enabled`, `cooldown`. `try_interact()` is the single duplicate guard. Emits `interacted(id)`. |
| Interactor | Area2D (on player) | Tracks overlapping Interactables and focuses the nearest. Handles `interact` in `_unhandled_input` and marks it handled. Emits `focus_changed` and `interacted`. |
| StoryTrigger | Area2D | Fires `triggered(id)` when the player enters. Latches if one-shot. |
| PuzzleController | Node | Wraps `core::SequencePuzzle`. Exports the solution ids and indicator nodes. States: Idle → Progress → Solved, with a timed Rejecting state on errors. |
| GameDirector | Node | Wraps `core::StoryProgress`, a forward-only beat machine: Shore → Abyss → Monolith → Awakened → Witness → Fleeing → Ended. Rejects duplicate and out-of-order events. Locks input, plays AnimationPlayer clips by naming convention, unlocks on finish. **A missing clip logs an error and skips the beat, so it cannot softlock.** Handles checkpoints and the ending scene change. |
| CameraRig | Camera2D | Follows the target with look-ahead (built-in smoothing and limits). `set_target` for cinematics. Trauma-based shake. |
| Hud | CanvasLayer | Prompt, fading captions, fade to/from black. |
| MenuController | Control | Title, pause and ending buttons. Pause toggle. |

This is 9 classes where the brief suggested 4 (Player, InteractionSystem,
Puzzle, Director). My reasoning: Area2D already *is* the interaction system,
so three ~80-line nodes beat a central manager. CameraRig, Hud and Menu exist
only because of the no-GDScript policy. If that policy is dropped, they become
GDScript and the C++ count is 6.

**Lifetime rules:**
- Nodes are owned by the tree. We never `delete` and never keep a bare
  `memnew` result.
- `Ref<T>` for every RefCounted object.
- Cache `T*` only for descendants; `ObjectID` for any other node.
- Connections use `callable_mp` (auto-disconnected when objects are freed).
- No static mutable state, and no exceptions (godot-cpp default).

**Testing:**
- doctest unit tests for the three core modules.
- A headless extension-load check.
- Headless integration tests under `--fixed-fps 60` with injected input
  actions. A hand-rolled ~80-line runner, no GUT. They cover:
  - landing, walking, jumping, walls
  - interaction focus, double press, one-shot
  - puzzle paths, trigger re-entry
  - cinematic lock and unlock, missing-clip handling
  - scene reload, editor wiring
- A 600-frame no-`ERROR:` smoke run.
- An export smoke test: the exported Linux binary runs
  `--headless --quit-after 300`.
- Manual playtests are reported separately.

**CI (GitHub Actions):**
- Linux and Windows builds in debug and release, using godot-cpp's own setup
  and cache actions.
- Unit tests on both OSes.
- Linux headless Godot tests against a pinned binary with a SHA-512 check.
- A release workflow that exports Linux and Windows from Linux and attaches
  zips to a GitHub Release.
- No secrets. itch upload is manual.

**Other choices:**
- Compatibility renderer, 480×270 viewport with integer scaling.
- Polygon terrain rather than a TileMapLayer.
- MIT for code, CC BY 4.0 for original assets, third-party assets CC0 or OFL
  only.

## 6. Where I want your scrutiny most

1. **Class split (D3) and the no-GDScript policy (D4).** Is 9 classes
   over-engineered for a 7-day jam, or is this the right granularity? Would you
   move UI and camera to GDScript?
2. **C++17/C++20 mixing (D2).** Is there any ABI or ODR hazard in linking
   C++20 translation units against a C++17-built godot-cpp static library
   (GCC 13 and MSVC 2022)? Is there a case for building godot-cpp itself with
   C++20?
3. **Lifetime rules.** Are there godot-cpp lifetime pitfalls I've missed? For
   example: `callable_mp` on Area2D signals during `reload_current_scene()`,
   `set_deferred("monitoring", false)` inside a `body_entered` callback, or
   Tweens outliving nodes.
4. **Duplicate-activation guards.** Is the combination of `_unhandled_input` +
   `set_input_as_handled` + `try_interact` cooldown + a forward-only story
   machine + one-shot latches sufficient? Can you find a sequence that
   double-fires a cutscene or locks input permanently?
5. **Headless testing approach.** Is a hand-rolled SceneTree runner with
   `--fixed-fps 60` and injected `InputEventAction`s reliable for
   `CharacterBody2D` tests in 4.7? Are there known flakiness sources?
6. **The exit-134 import abort.** Have you seen this behaviour with GDExtension
   on a clean cache? Is my CI workaround acceptable?
7. **Scope and schedule.** Does the plan fit 7 days for a one-developer team
   with no dedicated artist? What would you cut first?
8. **Puzzle design.** Is it understandable, and is it truly softlock-free?

Please do **not** propose new features unless they reduce risk.
